## Review of Specification: `1-values-md-standard-v0-1-the-va`

This is an exceptionally well-crafted specification. It clearly separates the *what* and *why* from implementation details, honors all baked decisions from the owner and architect, grounds its design in verified external documentation, and defines concrete, testable deliverables and validity rules (`V1`–`V9`).

Below are my findings and a few minor edge cases to tighten as you move into the planning and writing phases.

---

### 1. Clarity and Completeness of Requirements
- **Strengths:** The specification covers every required dimension—package shape, YAML frontmatter schema, Markdown body/core extraction, normative prompt texts, reinjection rules, fine-tuned model declarations, conformance levels, provenance, validity rules, marketplace mapping, and example packages.
- **Minor Ambiguities to Clarify in the Spec Text (`spec/`):**
  - **Character counting & whitespace normalization (Parts 3 & 11, Rules V4/V5):** The spec states limits are counted in "Unicode characters" (8,000 for body, 1,500 for core) and requires exact reproduction of expected rendered wrappers and reminders. When writing the RFC 2119 specification in `spec/`, explicitly specify:
    1. Whether "Unicode characters" means **Unicode scalar values (code points)** (as opposed to UTF-16 code units or grapheme clusters) and whether `\r\n` vs `\n` line endings are normalized before counting.
    2. Whether the core section extraction **excludes** the `## Core` heading line itself (Test Scenario 3 notes "the core is that section's content", which implies excluding the heading, whereas Desired State Part 3 says "It is the second-level section whose heading matches... running to the next first- or second-level heading").
    3. How leading and trailing blank lines around `{body}` and `{core}` are trimmed when substituting into the wrapper and reminder templates, so that byte-for-byte rendering comparisons (Success Criterion 10) are deterministic across implementations.

### 2. Technical Feasibility
- **Strengths:** The three-tier conformance model (Level 1: Prompt, Level 2: Tools, Level 3: Package) makes adoption very cheap for basic chat loops while scaling cleanly to full coding agents like Claude Code.
- **Claude Code Verification:** The spec properly identifies the two unverified Claude Code behaviors (whether extra files like `VALUES.md` at the plugin root are ignored, and whether plugin-less folders install cleanly via `marketplace.json`) as explicit test gates during implementation.

### 3. Edge Cases and Error Scenarios
- **Tag Breakout / Injection (Rule V6 & Part 3):**
  - Part 3 and Rule V6 forbid closing tags used by the normative texts (specifically `</values>`, `</value-system>`, `</value-system-reminder>`, `</value-systems>`).
  - *Suggestion:* Specify in the formal standard that the V6 check must be **case-insensitive** and allow for optional whitespace before `>` (e.g., `</values >` or `</VALUES>`), andconsider also disallowing opening `<value-system...>` tags inside the body so a package cannot spoof a second installed value system or reminder block inside its own body.
- **Multiple Active Value Systems & Reinjection (Part 10):**
  - When multiple value systems are active and use different `persistence.reinject.every-tokens` intervals, each package's token counter runs independently since its own text was last placed in context. Mentioning this explicitly in Part 10 of the formal specification will prevent implementers from sharing a single counter.
- **Marketplace Mapping for Optional Fields (Part 12):**
  - In the mapping table (Part 12), `version`, `license`, `tradition`, `languages`, and `tags` are optional in `VALUES.md` (with `version` recommended), and `steward.url` is omitted when `claim: individual`. Ensure the specification text notes that when an optional source field is omitted in `VALUES.md`, the corresponding key in the `marketplace.json` entry is omitted rather than emitted as `null` or an empty string.

### 4. Security Considerations
- **Strengths:** Security boundaries are well thought out:
  - No ambient discovery (mitigates repo-clone prompt injection).
  - No automatic execution of local hooks/scripts upon package installation, and hosts may decline local stdio MCP commands in `.mcp.json` (Rule V7 requires `https` for remote MCP servers).
  - No automatic switching to declared fine-tuned models without explicit user/operator choice, and fine-tuned models never replace the system prompt wrapper.
  - Character restraints on `steward.name` (1–100 chars, single line, forbidding `<`, `>`, `"`) prevent attribute breakout in `<value-system name="{name}" steward="{steward}">`.

### 5. Testing Strategy
- **Strengths:** The 27 test scenarios and the offline fixture requirement (`V1`–`V9`) are comprehensive, actionable, and verifiable without live model calls or network dependencies (aside from the explicit live check of the Ansari MCP endpoint). The zero-context reader test (Success Criterion 11 / Test Scenario 25) is an excellent test of specification clarity.
